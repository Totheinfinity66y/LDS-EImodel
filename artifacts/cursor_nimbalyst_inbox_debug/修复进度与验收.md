# Nimbalyst 运行中子消息消费修复与验收

状态：**PASS，已部署并重启载入，真实运行中收件及不重放验收通过。**

目标：A、定位主对话运行期间无法接收子报告的原因；B、修复接收与结束处理；C、实测同回合接收且不重复续接。

验证环境：Windows，Nimbalyst 0.81.7，Cursor CLI 2026.10.22-27dcf5f，Node v24.19.0。没有安装依赖、使用 computer use 或手工修改聊天数据库。

## 原因

1. `consume_session_inbox` 已有 schema 和 handler，却遗漏在 `HOST_TOOLS` 路由之外，正式 host 目录无法发现它。
2. inbox 的回合生命周期只为 Claude Code、Codex 初始化，没有覆盖 Cursor。
3. 原身份验证依赖 provider trace，且未覆盖 Cursor 格式。更深的故障是 Cursor 兼容链路的请求执行与 trace 写入不同步：等待日志来证明正在执行的工具，会出现循环依赖。
4. 兼容层还可能改写完成事件的工具名；仅按开始事件的完整工具形状匹配完成事件，会将已完成的旧调用误判为仍在运行。

子报告本来已经入队。运行中的父回合无法领取它，只能等回合结束后作为新输入投递，因此会造成等待不结束、结束后又被延迟通知唤起。

## 最终机制

host 正式暴露 inbox；Cursor 开始和结束回合时建立、退休 inbox。

Cursor 的正常收件入口采用**宿主实际处理的已认证 MCP 请求身份**。服务器闭包生成唯一作用域，结合 SDK 的 requestId，形成内部调用 ID；handler 将它绑定当前 Cursor session，再由 inbox 绑定当前运行回合和输入。这个证明通过内部参数传递，模型不能在工具参数中自行提供。未认证 HTTP 请求仍返回 401，未知 provider、错误工作区、已退休回合和伪造参数仍被拒绝。

领取报告继续使用原有事务：检查当前输入与 running 状态、领取准确的 FIFO 报告前缀、写 receipt；成功结束回合后将已领取报告退休为 completed。同 checkpoint 重试返回原 receipt，不重复领取。没有伪造 provider trace，也没有直接修改数据库状态来制造成功。

Claude Code、Codex 原有 trace 验证路径保留。Cursor trace 用于审计，不再作为兼容链路实时执行的必要前提；开始/完成的 ID 匹配也覆盖兼容层改写完成工具名的情况。

普通 report/status 可在当前回合消费；指令、问题、错误或附件仍保留队列边界。父对话在集成节点和最终回答前消费完整批次；无独立工作时结束回合，不轮询空 inbox，不向完成的子会话反复发送确认。自动完成通知已带 report 类型，显式发送进度回报应使用 `messageKind=report` 或 `status`。

```mermaid
flowchart LR
  A[子报告入队] --> B[运行中的父回合发起 MCP 收件请求]
  B --> C[宿主认证请求并绑定当前回合与输入]
  C --> D[事务领取并保存回执]
  D --> E[父回合读取报告并继续]
  E --> F[结束时退休报告 不再重放]
```
